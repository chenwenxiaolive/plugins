# MR merge and completion

Use this procedure for an explicitly requested merge, synchronization after its
authorized server-side rebase, or reconciling a merge already performed by the
user. Ordinary implementation ends at `ready-for-merge`. Read
[gitlab.md](gitlab.md) for access and [remote-workflow.md](remote-workflow.md) for
checkout ownership, remote validation and the review-round limit.

## Recheck before merging

1. Read the current MR, discussions, project merge requirements and persisted review status. If the MR is already merged, proceed to completion recording before attempting to fetch a possibly deleted source branch. Otherwise, fetch and record the full source SHA, current target-branch tip and merge-base; do not treat the MR's historical diff base as the current target tip. Confirm that acceptance, review and required validation evidence apply to this source and its integration with the current target.
2. Compare these values with the last passing review. If the source, target or agreed scope changed, assess the actual changes before reusing that verdict. Inspect effects on changed behavior, callers, dependencies, locks and tests even when the MR's own patch is unchanged. Record which evidence remains applicable and why; rerun affected required checks. Do not relabel a test run on an old SHA as a run on the new one. If the changed target must be incorporated to validate integration, use the authorized server-side rebase and synchronization procedure below before running those checks.
3. If the change invalidates the previous review, mark the MR's review-status section as needing review, update an issue still marked `ready-for-merge` to `active`, and use the next remaining corrective round for the full updated diff with the usual review command. Keep review details in the MR under the issue-record milestones. A merge request does not grant a new three-round allowance. If the allowance is exhausted, or validation or review cannot finish, leave the MR unmerged and report what needs human handling. An evidence-based check that the existing verdict still applies does not start or reset a review round.
4. Immediately before submitting the merge, read the source and target again. Any observed movement requires reassessing the affected evidence before proceeding. Submit the verified source SHA through GitLab's [merge API `sha` parameter](https://docs.gitlab.com/api/merge_requests/#merge-a-merge-request), using a supported CLI equivalent or the API. This guards the source, not the target. Respect the project's existing merge checks and do not bypass them. A rejected SHA or a changed baseline requires fresh inspection, not an unguarded retry. If continuing concurrent changes prevent establishing a validated baseline, report the blocker.

## Synchronize an authorized server rebase

A requested merge authorizes the forge's server-side rebase when needed by the
project's merge policy or the integration checks above. Wait for that operation
to finish and verify the resulting source SHA and any reported error before
changing a checkout. A successful rebase request alone is not completion.

1. Preserve the recorded pre-rebase source SHA, target SHA, merge-base and review evidence. Fetch the resulting source and target. Compare the old and new aggregate MR patches to confirm the changed-line content is unchanged; a commit-series comparison such as `git range-diff` can supplement this. Inspect any difference and apply the review rules above. Rebase success or absence of conflicts is not proof of equivalence.
2. Inspect the selected local checkout and each remote counterpart that will be updated. Require clean, idle checkouts, verify branch occupancy across linked worktrees and check jobs on every node sharing the remote storage. If a checkout is at the recorded old source and its divergence is solely the verified rebase, the steps below apply. Unexpected commits, dirty state, another branch owner or running jobs require resolving that condition first. Do not push the old history back to the MR branch.
3. If fast-forwarding to the verified source is possible, use the normal workflow. Otherwise, record the checkout path, old and new full SHAs, original branch, upstream and a unique archival branch name in the task's run directory before changing refs. Rename the old local branch to that archival name with non-forcing `git branch -m`, retaining its history and reflog. Remove the archive's upstream association. Recreate the original task branch with non-forcing `git switch -c` at the fetched, verified new source SHA, then set its upstream to the MR source branch. This retains one active development branch and an archival reference; keep the archive local.
4. Perform this independently in each distinct Git repository backing the selected local and remote checkouts, once per shared remote repository. Keep the checkout paths unchanged. Use neither reset, forced branch replacement, force-push nor a merge that reintroduces the pre-rebase commits. On interruption, inspect the original and archive refs and the recorded step: reuse a verified archive and finish the missing step rather than archiving again or replacing an existing ref. An unexpected ref value requires investigation.
5. Verify the original task branch name, correct upstream, clean state and exact new source SHA locally and remotely. Retain the archive names and old-to-new SHA mapping in the run record, with its location in the MR review status. Match the environment to the new commit's lock, rerun affected checks and complete the merge-time evidence assessment. Report the retained archives; do not delete them during this procedure.

The branch operations preserve the original reference before creating its
replacement: see Git's [branch rename](https://git-scm.com/docs/git-branch) and
[non-forcing branch creation](https://git-scm.com/docs/git-switch) documentation.
This procedure is limited to a verified authorized server rebase; it does not
authorize discarding unexplained local divergence.

## Record merge completion

- The agent executing the authorized merge reads back the MR until its actual outcome is known. An accepted request or queued merge is not a confirmed merge; leave the execution record in an accurate pending state if completion cannot yet be confirmed. Once merged, record the actual merge time and resulting merge or squash commit reported by the forge in the MR review-status section.
- A gateway error or timeout from the merge request is not a failed merge; do not resubmit it. Read back the MR and fetch the target. If the target holds a merge commit whose parents are the recorded target and the verified source SHA, the merge is complete in Git even if the MR stays open: record that commit and its time as the merge result, close the MR with a note naming the commit instead of merging again (a second merge only adds an empty merge commit), and delete its source branch if its tip is the verified SHA. Keep the merge call's raw response (`glab api -i`) in the run directory so its headers show which layer answered. Observed on 2026-10-20: a 504 after about 60 s, the merge commit written but the MR left open.
- That agent updates the existing issue execution comment to `merged`, retaining its branch and MR links and adding the confirmed merge commit and time in the status. Only update the record for this MR; do not overwrite a newer assignment. Keep the Worktree field accurate: merging does not itself release a checkout or stop its jobs. If the issue remains open, report its actual state; do not close an incomplete parent or unrelated issue.
- If the user merged in the UI, the next agent reading the task or reusing its worktree performs the same read-back and record update before treating the task as unfinished or paused. No background poller is required. Do not recreate or push a deleted source branch merely to reconcile a completed task. Release the worktree only after the usual clean-state and job checks.
