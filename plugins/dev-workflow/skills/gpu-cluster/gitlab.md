# Internal GitLab access and authentication

<!-- Moved from ~/.claude/CLAUDE.md on 2026-10-16; the always-loaded rules there still apply. -->

- The current internal GitLab endpoint is **`http://gitlab.iquest-inner.com/`**. References to `https://gitlab-cn-beijing.siflow.cn/` in repository documentation, scripts, dependency declarations or locks may be historical; they do not override this access guidance. A failure at the old endpoint does not establish that the user lacks permission.
- The current local agent environment already provides `GITLAB_TOKEN`, `GITLAB_HOST=gitlab.iquest-inner.com`, `GITLAB_API_HOST=gitlab.iquest-inner.com`, `GLAB_API_PROTOCOL=http`, `GH_TOKEN`, and Git credential/identity settings through `GIT_CONFIG_COUNT`. Prefer these existing settings; recheck variable presence in a new session instead of assuming credentials exist only on the nodes.
- GPU nodes and gates already provide authentication/tool settings in their remote sessions. An SSH `Include` line alone does not establish that credentials are injected; verify required variable presence in the actual session. If the local session lacks the needed tool or credentials, use `sh-gate`, `zg-gate`, or a GPU alias from machines.md, following the checkout `cd` rule for project commands. Check credential-variable presence only when needed; never dump the environment, SSH `SetEnv` values, or `GIT_CONFIG_VALUE_*`. Do not embed credentials in command arguments, Git remotes, logs, repository files or chat. Never print a credential file, even redacted; check one with `test -s`.
- OSS credentials for jobs: `source /volume/.config/oss/<account>.env` in `run.sh` (`qr` for bucket skyinfer-qr, `zg` for skyinfer-zg). Each file sets `OSS_ACCESS_KEY_ID`, `OSS_ACCESS_KEY_SECRET`, `OSS_ENDPOINT` and `OSS_REGION`. The control machine's copy is the source. For an authorized credential deployment, `profile.sh push <gate>` deploys it with the rest of `.config`; choose `sh-gate` or `zg-gate` for the intended cluster. Both gates have rsync.
- Local `gh` and `glab` authenticate from the inherited `GH_TOKEN` and `GITLAB_*`/`API_PROTOCOL` variables, with no login step; Git operations use Git's existing authentication. Prefer `glab` for GitLab issues, MRs and API calls. `gh` reaches GitHub directly.
- On this control machine, `glab` already has the per-host proxy configured by `glab config set proxy http://127.0.0.1:18080 --host gitlab.iquest-inner.com`. Use plain `glab` commands; no `HTTP_PROXY=...` prefix is needed. This setting uses the existing local tunnel and applies only to this GitLab host. If the setting is absent in another local environment, use a command-scoped `HTTP_PROXY=http://127.0.0.1:18080` as a fallback. GPU nodes and gates use their own network configuration; do not copy this loopback proxy setting to them.
- In the selected checkout, let `glab` infer the repository and host: `glab issue list`, `glab issue view <iid>`, `glab mr list`, or `glab api projects/:id/issues/<iid>/notes`. Prefer built-in issue/MR commands when they cover the query; use `:id` in API paths instead of spelling out the URL-encoded project path. Use `-R <group>/<project>` for issue/MR commands targeting another repository and `--hostname` only when an explicit host override is needed.
- `--jq` filters the JSON output of `glab` commands that emit JSON, such as `issue`/`mr` `list`/`view` with `--output json` (glab 1.100+). `glab api` has no `--jq` in any release, locally or on gate: pipe its JSON to `jq` and select only the fields needed. `gh api` has `--jq`.
- `glab auth status` reporting no configured login does **not** establish that environment-variable authentication is unavailable. Verify access with an actual read-only request to the intended repository, such as `git ls-remote` against its current HTTP URL or `glab api projects/:id` from its checkout with the inherited API protocol and credentials.
- For a dependency whose script still defaults to the old host, prefer a supported per-command repository override (for example `MEGATRON_REPO_URL`) while preserving the required repository and commit. Do not change dependency pins, persistent remotes or shared network configuration merely to diagnose authentication.
- From this control machine, access `http://gitlab.iquest-inner.com/` through the existing HTTP proxy on `sh-gate` via the local SSH tunnel at `http://127.0.0.1:18080`. This loopback proxy address is local to the control machine; nodes use their existing network and proxy configuration. The hostname is resolved inside the remote network by the proxy.
- The tunnel is managed by `gate-proxy-tunnel.service`, enabled at boot and configured to reconnect automatically. Its unit is `/etc/systemd/system/gate-proxy-tunnel.service`; it forwards local `127.0.0.1:18080` to `sh-gate`'s `127.0.0.1:18080` using the `sh-gate` SSH alias.
- Local Git has a URL-specific global proxy setting for `http://gitlab.iquest-inner.com/`. For raw HTTP requests outside `glab`, use `curl --proxy http://127.0.0.1:18080 --noproxy '' http://gitlab.iquest-inner.com/...`. Other clients need their own proxy option or proxy environment variables scoped to that command.
- An unauthenticated API request can return `401`; retry using the existing authentication before concluding that additional access is needed. Use HTTP: HTTPS to this host has timed out; do not disable certificate verification.
- If access from this control machine fails, inspect `systemctl status gate-proxy-tunnel.service` and test the local proxy before changing any network configuration. Changes to gate's shared proxy affect other nodes and require an explicit request.
- Clone success does not establish push permission; check the intended origin and authentication when first synchronizing a project. Use the development workflow in remote-workflow.md.
- Request authentication help only after checking the current endpoint, the applicable proxy/network path and the existing credential environment, and confirming that the intended read-only request still fails. Report the host, operation and sanitized error; do not ask the user to paste a token into chat.
- GitLab closes an issue when a commit merged to the default branch contains a closing keyword (`closes`, `fixes`, `resolves`) before the issue's reference, squash messages included. Use one only to close that issue; for one item of a tracking issue write `#<N> item <X>` instead.
- For a requested merge, follow [merge-workflow.md](merge-workflow.md) for current-source and target checks, server-side rebase synchronization, and execution-record updates.
