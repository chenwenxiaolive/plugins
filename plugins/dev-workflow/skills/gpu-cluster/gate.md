# Gate operations and deployment configuration

- Maintain cluster-ops in the real local Git checkout `/volume/cluster-ops`, origin `https://gitlab.iquest-inner.com/xqing/cluster-ops.git`. Gates use the same absolute deployment path. This is the selected exception to the usual `/volume/workspace/<project>` layout.
- The control machine's `/volume/.ssh`, `/volume/.bashrc`, and entire `/volume/.config` directory are the saved configuration for future gate deployments. GitHub, GitLab, Git, rclone and OSS account files are under `.config/gh`, `.config/glab-cli`, `.config/git`, `.config/rclone` and `.config/oss`. These private files stay outside Git and Docker images. Changes here reach a gate only when deployed; independent clusters do not share these local files.
- For an explicitly requested new gate deployment, run `/volume/cluster-ops/bootstrap-gate.sh <ssh-alias> --dry-run` from the control machine, review the transfer, then run it without `--dry-run`. It copies the saved configuration and ops files (excluding `.git`), then runs `gate-proxy.sh start` and `status`. It requires root SSH access, a writable `/volume`, and the development image's tools and shell startup hooks; it does not create the pod or install the image.
- Saved deployment configuration and live gate configuration can differ, `.bashrc` and authentication included. Preview a deployment with `profile.sh push <gate> --dry-run`, check effective settings before diagnosing authentication, and preserve any existing gate checkout changes.
- The Dockerfile installs rclone at `/usr/local/bin/rclone`, but a gate can run an older image; check `command -v rclone` and `rclone version` there.
- `/volume/.gate-proxy/remote-hosts` is persistent configuration specific to each cluster. Preserve it; it is not obsolete proxy runtime state and is not included in the bootstrap configuration list.
